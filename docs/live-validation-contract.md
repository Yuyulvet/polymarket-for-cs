# 赛中细粒度预测：后续验收契约

状态：2026-09-16 已开始落地旧赛中实验修正，详见 [修正与重建说明](inplay-fixes.md)。
尚未实现经过验证的实时游戏事件接入，也未启用赛中交易。
用户提出的假设是：更细的游戏过程可以提供额外预测信息。应按粒度逐层检验，而不是预设越细必然越准。

## 现有资产与阻断项

已有离线击杀/炸弹事件、存活人数、HP、经济档位及几何位置摘要，可作为重建实验的原料。
现有 `live_state.py` 只提供系列赛比分和外部赔率，不能等价提供这些局内特征。
HLTV 赛前接入核实地图与本场名单；后续新增的独立 raw live 原型本次连接返回 403，
不等于已获得稳定低延迟局内事件流。详见 [采集实测记录](hltv-live-capture.md)。

下列为整改前发现的问题；旧成绩和旧缓存仍不能直接作为新模型验收依据：

- `midround.py` 的 30 秒状态使用全回合首杀方向，存在未来事件泄漏。需要以截止 tick 截断后重新构建新缓存。
- `inround_model.py` 混合终局与未结束事件。炸弹已经爆炸/拆除等确定状态不能算作“预测本回合”的能力；
  已结束回合可以作为后续回合/仍未结束地图预测的已知历史，两类目标必须分开。
- `forward_sim.py` 按系列赛而非单图串接回合，并以先到 13 分停止；不能复用为正确的 MR3 加时地图胜率模拟。
- 旧 ADR 包含护甲伤害；位置 aiming/contact 只是几何代理，不等于考虑墙体、烟雾和垂直遮挡的真实视线。
- `inplay_data.py` 用系列赛开始时间加各回合有效比赛长度重建 UTC，遗漏冻结、暂停和地图间隔，不能证明秒级对齐。
- 历史分钟价格没有完整盘口及真实收到时间；`realtime_record.py` 旧记录也只保留顶档和本地时间，不能替代全深度成交回放。

整改采用新版本数据，保留旧缓存和旧报告。代码修好不等于旧产物已自动变成无泄漏数据；
必须显式重建，再进行概率评估。用户已有的 `inplay_data.py` 修改保持不动。

## HLTV live 候选源核实（2026-09-16）

HLTV 确实提供 scorebot/livescore 功能；官方历史说明也提醒服务器配置、崩溃和回合恢复可能使更新不完整。
这能支持“HLTV 是候选来源”，不能证明每场均有完整击杀、HP、装备、坐标，或稳定零延迟。
后续已尝试一次公开 scorebot WebSocket 连接，但握手返回 HTTP 403，未收到事件。
当前协议兼容性、字段覆盖和相对 Polymarket 的端到端延迟均未验证。

更重要的是，HLTV 现行条款（页面标注 2025-01-27 生效）2.2 明确限制数据挖掘/网页抓取，
3.2 要求业务用途获得许可。公开免费浏览不等于自动化采集、训练或交易用途已获授权。
用户随后要求继续开发，已新增单次、短时、独立采集原型，并在真实 403 后停止，没有规避限制。
这不代表已解决使用许可。自动化长期运行前应获得适当许可或使用赛事方/供应商允许的源；
本轮没有购买或对外联系，也未启用模型或交易消费这些消息。

即使许可明确，也要先录制少量真实赛事并核对：完整初始化状态、击杀/下包/回合事件覆盖、
状态重置与重连、源时间/本地接收时间、可对应的市场，以及盘口到达先后。不能用价格相关性
反推一个“最优延迟”再回填历史决策。没有可信源 UTC 时，源延迟应标为未知。

来源：[HLTV livescore 官方说明](https://www.hltv.org/news/18733/introducing-livescore-and-filtering)、
[HLTV 现行条款](https://www.hltv.org/terms)。

## 同步不仅是两个画面同时刷新

至少保存并区别以下时间，不得互相冒充：

1. 游戏事件源时间：原始 tick/游戏时钟；若有可靠 UTC 锚点，保存锚点、时钟误差和来源证据。
2. 游戏事件本地收到时间：UTC 与单调时钟，含源事件 ID、顺序号、回滚/修正标记。
3. 盘口源时间与盘口本地收到时间：两者都保留，连同完整簿、增量及重同步记录。
4. 特征完成、推理完成和决策时间：只能使用此前确实收到的数据。
5. 模拟允许成交时刻：再加客户端和该市场实际执行延迟，只用此后真实观察到的可成交深度验证。

例如某次击杀源时间为 10:00:01，但本系统 10:00:03 才收到；其他参与者可能已在 10:00:02 改价。
不能把这条击杀回填到 10:00:01 的决策，更不能用旧价格假定成交。
没有可信源 UTC 时，可以按本地收到时间做前向观察，但必须把源延迟标为未知，不能宣称测得秒级领先。

Polymarket 的公开市场 WebSocket 提供 book/price_change 等事件及服务端 timestamp；这不替代本地到达时间。

自 recorder schema v3 起，normalized book 还保存 L1/L5 depth、top-five
levels、spread、midpoint 和显式 trade fields。相关 P0 研究口径与已发现的
历史 recorder 缺陷见 `docs/market-microstructure-p0.md`。旧 schema 缺少的
depth 不得以 0 填充，也不得用于声称完成了 liquidity/OBI 分层验证。
字段依据：[官方 Market Channel](https://docs.polymarket.com/api-reference/wss/market)。

## 事件/状态最低要求

- 稳定系列赛、单图实例、地图序号、阵容与 outcome/token/condition 映射；换边不改变队伍身份。
- 状态至少明确比分、当前 CT/T、回合阶段、加时阶段、可用经济/装备、人数、HP、炸弹与剩余时间。
- 离线特征应来自同等可见的信息范围；赛后 demo 全知状态不等于实时时刻可获得的观察。
- 缺帧、乱序、未来时间、身份变化、断线和过期都要可检测；未重同步前不生成可执行信号。
- 处理暂停、恢复、重赛和事件更正；新证据不能回写旧决策。已经持有的模拟仓位与待成交信号分开处理。
- 不同源时钟误差与比赛转播延迟单独记录；只靠价格相关性寻找“最佳对齐”会产生事后选择偏差。

## 第 3 步落地评估（2026-09-16，基于第 2 步粒度结果）

第 2 步已定案（`data/map1/research/full-map-research-l4-20260916/`，诊断性质）：
比分阵营 −0.0882 → +回合经济 −0.0019 → +存活/HP/炸弹 −0.0042 → +位置/武器/结构 **+0.00005（零增量）**。
因此 live 必需字段收敛为：比分/阵营/回合（L1）+ 回合开始装备（L2）+ 存活/HP/炸弹状态（L3）；
位置追踪、武器分类、攻防结构无需上线（无模型增量）。

### 契约三问的现状回答

1. **字段是否提供**：商业源（PandaScore/EsportsOdds/GRID）口径上覆盖 L1–L3；HLTV 免费路径页面可见但自动化条款受限、WS 握手 403。
2. **是否过期/含回放**：未验证——这是订阅后第一件事：录少量真实场次，核对初始化完整性、
   击杀→帧延迟（PandaScore 自注 frames 约 2s 间隔，is_alive 可能滞后于 kill）、暂停/重赛处理。
3. **盘口到达与模型判断时间**：未验证——需要同期录 Polymarket book（`creation_record.py` 已具备）
   与游戏事件源，按契约区分 5 类时间，不能拿价格相关性回填"最优延迟"。

### 结论与决策点

瓶颈不是模型（L3 层有真实增量），是**带许可的实时源**。免费 HLTV 路径条款阻断且技术未通；
商业源里最便宜的验证成本是 EsportsOdds（$99/月）或 KashRock（$29/月起，含沙盒）。
建议决策顺序：① 用户确认是否申请 GRID 免费研究档（需对外联系）；② 或小额订阅最便宜的源做
契约要求的源验证；③ 两项都不选则 live 路线保持冻结，离线粒度研究继续但不接交易。
在拿到可信源并完成上述验证前，任何 live 模型（含 L3）都不得进入纸面交易评估。

### 直播画面前瞻协议 v1（2026-09-17 冻结）

首次探索的数据不进入本协议。旧版 session 没有强制赛事绑定和人工比分事件文件，分析器会拒绝读取。
下一批全新比赛固定使用以下规则，收齐一批之前不改参数：

- 每个采集 session 必须绑定 Polymarket `event_id`、两个 outcome 的原文队名、地图序号和精确
  `Map N Winner` 市场。直播页标题不作为身份依据。
- 正式采集第一帧同时保存全画面和比分区。人工在该帧确认直播左右队名与绑定两队相同、地图序号相同；
  左右顺序可以相反，确认文件负责映射。任一不符即隔离 session，运行中的观察器检测到隔离文件后停止。
- 画面以 1 秒采样；候选像素阈值固定 0.10、冷却固定 8 秒。原始事件名为
  `candidate_visual_change`，本身不代表比分变化，也不得进入分析。
- 每个入选事件必须人工检查候选前后截图：比分板均清晰可见、两队仍匹配、只有一队比分恰好增加 1。
  已核验事件还必须与上一条已核验比分连续；漏回合、转场、回放、暂停图、接管图全部排除。
- 盘口采用 2 秒分箱中位价，前后持续位移阈值固定 0.03；二元 outcome 在 3 秒内的镜像变化合并。
  配对窗固定为 ±60 秒，一对一最近匹配，而且只接受价格朝本回合得分队方向移动的跳变。
- 只报告本地收到时间之差；直播自身延迟仍未知，因此结果叫“画面—盘口到达差”，不叫游戏事件源领先。
- 第一批最低门槛为 5 场不同系列赛、至少 30 个连续且可核查的比分递增事件。达到门槛前不判断优势，
  不改阈值，不接纸面下单，更不接实盘。

实现入口：`cs2ml.stream_score_watch` 负责带身份采集候选前后帧；
`cs2ml.stream_score_verify` 负责身份确认和严格比分递增核验；`.scratch/stream_lag.py` 只读取
`verified_score_events.jsonl`，并再次检查 session 身份、地图和盘口方向。

### 5E 事件流与连杀超调实验（2026-09-17）

`cs2ml.fivee_live` 已升级为 schema v2。默认不会因连续网络错误退出，而是在限定采集时长内指数退避重连；
每次轮询、错误、恢复和结束均写审计记录。首次全量快照与断线后的恢复快照分别标为
`initial_snapshot` / `recovery_snapshot`，两者的 `decision_eligible=false`。跨进程重启可用
`--resume-from` 预载旧事件键，完整 `log_info` 参与哈希，避免旧版 64 字符前缀碰撞。

首个“连杀后反向交易”回放入口为 `cs2ml.swing_overreaction`。规则固定为：同回合、同队连续至少 2 次击杀，
相邻击杀不超过 8 秒；以首杀前 5 秒中价为基准，末杀后 2 秒若击杀方价格上移至少 0.03，按另一方真实卖一
买入，并在 15/30/60/120 秒后按真实买一卖出。报告同时保留毛收益与按显式费率假设计算的净收益；中价从不
充当成交价，重叠事件的收益不得相加冒充组合收益。

MOUZ–NRG Map 1 的旧数据只能按 5E `update_version` 做市场反应研究：30 个连杀链中 20 个有盘口覆盖，
阈值触发 5 个；使用 0.05 费率假设时，四个持有期的平均净收益均为负。严格本地接收模式没有一个合格事件，
因此当前结论是“这一张图不支持连杀反向策略”，而不是策略已被普遍证伪。第一批验收门槛仍是至少 5 场系列赛、
30 个 schema-v2 严格接收事件；达到前只做纸面记录，不调参、不实盘。

## 粒度实验顺序与验收

固定赛前先验 → 已结束回合的比分/阵营 → 回合开始经济 → 局内人数/HP/炸弹 → 位置、武器、道具和攻防结构。

每层都使用同一批未来系列赛/地图和同一批未终局可预测时点；同系列赛所有地图、所有事件归于同一时间分区。
特征计算、标准化、训练、校准和筛选只能使用过去；不能用全回合最终结果构造较早状态。
模型可以直接预测地图结果，也可以先预测回合再推演地图；后者必须正确处理经济转移、换边和加时。

分别报告回合目标与地图目标的 Brier、Log loss、校准，以及与当时市场的增量；不能把回合概率当地图概率。
统计不确定性以系列赛聚类，并检查时间/赛事集中度，不能把几十万条事件当独立样本。
最终测试还需延迟、滑点、盘口深度和费用压力；更多细节或时间对齐本身都不能保证净期望为正。
