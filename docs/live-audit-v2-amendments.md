# 会话审计口径 v2 修订（live-audit-v2）

生效时间：2026-09-21（决赛 `manual-1053479-omc2398108` 收尾后首次执行）
适用方式：对**全部历史会话**（2026-09-19 起所有 `data/live_sessions/` 会话）按 v2 重审，
与 v1 报告并列存档，不覆盖、不删除任何 v1 报告与原始数据。

## 修订纪律（先于重审立此存照）

1. 每条修改都由**与具体会话结果无关**的工程事实驱动（下文逐条列事实）；
2. 全部历史会话一视同仁重审，不挑数据；
3. v1 阻塞原因保留在报告的 `v1_blocking_reasons` 字段中，永可对照；
4. 冻结的交易/策略规则（波段方案、验收账本判据）**完全不受影响**——本修订只动
   「采集质量闸口」，不动「edge 判据」。

## R1：段完整性 —— 操作员重启续采不算段缺失

**工程事实**：`live_session_run` 的续采是设计功能（`market_raw_capture` resuming 模式、
`FiveERecorder.load_seen` 去重续写）。进程因系统内存被杀、或因工程修复需要主动重启时，
第一段记录天然没有 `session_end` 行。5E 两个记录器的 `session_start`/`session_end`
行由进程自身在自然结束时写入，被杀段无法补写——**补写即伪造证据，禁止**。

**v2 规则**：一个缺 `session_end` 的段可接受，当且仅当同一文件内存在后继 `session_start`，
且新段首行时间与该段末行时间之差 ≤ `MAX_RESTART_GAP_SECONDS = 300`。超出间隙或段后再无
记录 → 仍阻塞（`segment_missing_session_end`）。报告新增 `restarts_detected`。

**为什么不是救数据**：重启恢复是采集系统今后的常规运维操作（每次崩溃、每次代码修复后
续采都走同一路径）。300 秒间隙上界保证「隔天重启」不会被误认连续。

## R2：盘口 normal-end —— 赛后干净关闭按覆盖完整性认定

**工程事实**：CLOB 服务端会在比赛结束后空闲期干净地关闭 WebSocket（recv 返回空）。
2026-09-20 半决赛观察到：比赛 21:45 结束，盘口 22:08 空关闭，**磁带覆盖完整场**。
空关闭不重连曾是代码缺陷（bug4 漏网路径，2026-09-21 凌晨已修），修复前会话的
`exit_reason=connection_closed` 标记反映的是代码缺陷而非数据缺失，且其完整性**可验证**。

**v2 规则**：`normal_end` 成立若 ① `exit_reason ∈ {deadline, stop_file}`（同 v1），或
② `exit_reason == "connection_closed"` **且**盘口磁带覆盖结束时间 ≥ 最后一场内事件时间
− 60 秒（磁带至少覆盖到我们知道的最后一场比赛事件；终端回合观测仍按 R3 逐图核验）。
「最后一场内事件时间」= 事件流中最后一条 `record_type=event` 行的时间，**不是**记录器
hours-deadline 的 `session_end` 时间——记录器赛后空转会继续 poll 到 deadline，其末行
不代表比赛还在进行（2026-09-20 半决赛实测：末场事件 13:35，盘口 14:08 空关闭，
session_end 15:45）。`exit_reason == "error"`（异常路径）与赛中 `byte_limit` 不做此
宽免——磁带确实断在赛中，完整性不可声称。

**为什么不是救数据**：宽免只给「可交叉验证的赛后干净关闭」这一类，认定条件（覆盖到
事件流末端）对所有会话通用；赛中死亡照旧拒。

## R3：round-one/terminal 闸 —— 会话级改为逐图级

**工程事实**：5E 公共事件日志对**部分地图的第一图**存在系统性发布延迟——连续三个比赛夜
观察到 Anubis 作为图一时日志缺失前若干回合（Inferno/Mirage/Dust2 作图一均正常）。
该缺失发生在**源端**，任何轮询策略都拿不到，属不可控观测局限而非采集事故。

**v2 规则**：逐图判定 `bout_status ∈ {complete, incomplete_no_round_one,
incomplete_no_terminal, unobserved}`。会话合格条件从「全部图完整」放宽为
「**至少一张期望图 complete**」；`incomplete_*` 图的全部决策行被数据集构建器排除
（整图排除，含后段回合——宁可保守，不做" cumulative 分数反推前段"的复杂认定）；
`unobserved`（该图无任何事件，如短局未打到的图）不阻塞、不产生行。
`no_strict_eligible_mqtt_snapshots`、`insufficient_three_source_overlap` 等
其余闸口**不变**（它们保障的是行级时间对齐，与图级观测无关）。

**为什么不是救数据**：放宽的是「观测局限的归因」——源端不发布的数据谁采都没有；被排除的
图在行级照样进不了数据集。每多一个合格图仍然要求 round1 与 terminal 都亲眼观测到。

## 已知代价（如实记录）

- v2 后 2026-09-20 半决赛（盘口赛后空关闭 + Anubis 图一）与决赛（重启续采 + Anubis 图一）
  预计转为合格（各含 1+ 张完整图）；2026-09-19 四场中仅 Aurora 场可能受益（其余场
  盘中断/凭证死循环属 R2 不宽免的赛中死亡），以其重审结果为准。
- 合格的 Anubis 第一图永远不会产生早段触发点样本——这是源端决定的样本结构，不是口径缺陷。
